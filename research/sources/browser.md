# Browser in sandbox: sources (accessed 2026-10-13)

## 1. Chromium in gVisor
- No official gVisor doc or test page covering Chrome was found; a GitHub search of google/gvisor issues for "chrome"/"chromium" returned no Chrome-specific bugs. UNVERIFIED that gVisor tests Chrome. https://github.com/google/gvisor/issues?q=chrome
- Evidence it runs in practice: GitHub's gh-aw-firewall runs recurring "Smoke Playwright gVisor" CI jobs (Playwright-driven Chromium under runsc). https://github.com/github/gh-aw-firewall/issues/7945
- A third-party write-up says GKE Agent Sandbox (gVisor) needs `--no-sandbox`, reports a 1.5-2x slowdown on screenshot-heavy sessions, and recommends `--disable-dev-shm-usage`. It blames a clash between gVisor's seccomp handling and Chrome's seccomp-bpf. Single blog, so treat it as UNVERIFIED. https://ghchinoy.medium.com/sandboxing-browser-agents-isolation-options-for-go-chrome-0c1bf3afbfbf
- User namespaces in runsc are still incomplete. Open issues cover a caller-configured userns with a non-root uid, and runsc not advertising userns support to CRI (`hostUsers: false`). That makes Chrome's namespace sandbox fragile. https://github.com/google/gvisor/issues/13564 , https://github.com/google/gvisor/issues/13303
- Shared-memory gaps: `MADV_REMOVE` is not supported (open issue), and that call relates to shm/memfd usage patterns in browsers. Its effect on Chrome is UNVERIFIED. https://github.com/google/gvisor/issues/4900
- Puppeteer's stance: running without a sandbox is strongly discouraged. "No usable sandbox!" comes from userns being blocked (for example by Ubuntu AppArmor). https://github.com/puppeteer/puppeteer/blob/main/docs/troubleshooting.md
- Standard container flags are `--no-sandbox` (root), `--disable-dev-shm-usage` (small /dev/shm), `--disable-gpu`, and sometimes `--no-zygote`. https://webscraping.ai/faq/headless-chromium/how-do-i-optimize-headless-chromium-for-continuous-integration-pipelines
- `--headless=new` combined with `--no-sandbox` has been reported flaky in Kubernetes. https://github.com/puppeteer/puppeteer/issues/10367
- Practical read: with gVisor the outer sandbox replaces Chrome's inner one, so expect to run `--no-sandbox` and mount a large tmpfs at /dev/shm (or pass `--disable-dev-shm-usage`). Inference, UNVERIFIED by an official source.

## 2. Chromium in Firecracker / Cloud Hypervisor
- Firecracker boots a Linux kernel directly with no BIOS. The guest init/rootfs decides /dev/shm and namespaces, so mount a tmpfs at /dev/shm and enable CONFIG_USER_NS and CONFIG_SECCOMP_FILTER in the guest kernel if Chrome's own sandbox should stay on. The kernel-config claim is inference, UNVERIFIED. https://lwn.net/Articles/775736
- Freestyle (VM-based sandboxes) documents headless Chromium with `--headless=new --no-sandbox --disable-dev-shm-usage --remote-debugging-address=127.0.0.1 --remote-debugging-port=9222 --remote-allow-origins=* --user-data-dir=...`. Headed mode drops `--headless` and sets `DISPLAY=:0`. It warns that browser package installs can OOM a small VM. https://www.freestyle.sh/docs/guides/run-chromium-and-chrome-in-a-sandbox.md
- No GPU in Firecracker means software rendering (SwiftShader / llvmpipe via `--disable-gpu`). No source measured the cost. UNVERIFIED.
- Fonts: minimal rootfs images need font packages installed explicitly, or pages render as tofu. Common practice, no authoritative source found. UNVERIFIED.
- Entropy: snapshot clones share RNG state. Firecracker recommends deleting the systemd random-seed before snapshotting, attaching virtio-rng, relying on VMGenID (Linux 5.18+), and explicitly reseeding on older kernels. `boot_id` is identical across clones. https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/random-for-clones.md
- Kernel's browser image needs at least 8 GB of memory for the unikernel build. Mutter and tint take a few seconds on first boot. https://github.com/kernel/kernel-images

## 3. GPU options
- gVisor nvproxy supports the driver capabilities `compute`, `utility`, `graphics`, and `video`. Only compute and utility are on by default, and the others need `--nvproxy-allowed-driver-capabilities`. The docs say Vulkan and NVENC/NVDEC are supported and do not mention OpenGL. Chrome GPU raster through Vulkan under nvproxy is therefore plausible but untested here, UNVERIFIED. https://gvisor.dev/docs/user_guide/gpu/
- nvproxy's supported-GPU list covers datacenter parts (T4, L4, A100, A10G, H100). https://godocs.io/gvisor.dev/gvisor/pkg/sentry/devices/nvproxy
- Cloud Hypervisor supports VFIO PCI passthrough, including NVIDIA GPUs (GT 710 example, GPUDirect P2P). Snapshot or migration with VFIO needs a migration-v2 variant driver, and generic `vfio_pci` is not migratable, so a passed-through GPU blocks snapshotting. https://github.com/cloud-hypervisor/cloud-hypervisor/blob/main/docs/vfio.md
- Upstream Cloud Hypervisor has no virtio-gpu. Spectrum OS maintains an out-of-tree patchset (crosvm vhost-user GPU) described as "likely not upstreamable", with builds up to CH 50.0. https://spectrum-os.org/software/cloud-hypervisor , https://lists.spectrum-os.org/archives/list/discuss@spectrum-os.org/2024/2/
- Firecracker supports no GPU at all (no PCI passthrough or virtio-gpu in its device model). https://github.com/firecracker-microvm/firecracker (device model; UNVERIFIED for any 2026 change)

## 4. Remote control over CDP
- Chrome 136+: `--remote-debugging-port` and `--remote-debugging-pipe` are ignored for the default data directory and must be paired with a non-default `--user-data-dir`. Chrome for Testing keeps the old behavior. https://developer.chrome.com/blog/remote-debugging-port
- A cua project report says the switch is still ignored on the default profile in Chrome 151. https://github.com/trycua/cua/issues/2916
- Old headless was removed from the Chrome binary in Chrome 132, so `--headless` now means new headless (full Chrome). The old engine ships separately as `chrome-headless-shell` (since 120), which has fewer dependencies and needs no X11 or D-Bus. https://developer.chrome.com/blog/removing-headless-old-from-chrome , https://developer.chrome.com/blog/chrome-headless-shell
- `--remote-debugging-address`: reports suggest recent Chrome binds only to localhost and ignores it, while chrome-headless-shell still honors it. Conflicting sources, UNVERIFIED. https://makandracards.com/makandra/624227-updated-capybara-running-tests-headless-chrome?page=1
- Recommended pattern: bind CDP to 127.0.0.1 inside the sandbox and expose it through a proxy or forwarder (socat/ncat, or vsock forward to the host). Kernel exposes 9222 through `ncat` and clients read `/json/version` to get `webSocketDebuggerUrl`. A unikernel needs a Host header. https://github.com/kernel/kernel-images
- Freestyle uses a loopback bind plus `--remote-allow-origins=*` for clients reaching it through a WebSocket proxy. https://www.freestyle.sh/docs/guides/run-chromium-and-chrome-in-a-sandbox.md
- Playwright docs say `connectOverCDP` is "significantly lower fidelity than the Playwright protocol connection", works only for Chromium, and requires Playwright's launch args if the browser was launched externally. `launchServer` + `connect()` needs matching client and server major.minor versions, and anyone who knows the `wsPath` controls the OS user. https://playwright.dev/docs/api/class-browsertype

## 5. Headful stack for computer use
- Anthropic's computer-use reference container is an X11 + VNC Linux desktop. It serves noVNC on 6080 (`/vnc.html`), VNC on 5900, and the web UI on 8080, with `WIDTH`/`HEIGHT` set by env and a recommended resolution of 1024x768 (XGA). The Dockerfile (Xvfb + mutter + x11vnc + noVNC) was not inspected, so the component list is UNVERIFIED. https://github.com/anthropics/claude-quickstarts/tree/main/computer-use-demo
- Kernel's headful image runs Chromium with mutter and tint2 and a live view on 443. The default is noVNC, and optional WebRTC (adapted from neko) is much faster and supports resize and clipboard. https://github.com/kernel/kernel-images
- OpenAI CUA sample app stack: not fetched, UNVERIFIED.
- Per-session memory, CPU, and cold-start measurements comparing headless and headful: no authoritative measurement found, UNVERIFIED. Freestyle notes OOM risk on small VMs. https://www.freestyle.sh/docs/guides/run-chromium-and-chrome-in-a-sandbox.md

## 6. Browser-for-agents products
- Kernel: moved from Docker with warm pools to Unikraft snapshot-based microVMs and reports 10x faster cold starts and zero idle cost (vendor case study). https://unikraft.com/customer-stories/scaling-browser-infrastructure
- Kernel unikernel standby snapshots state when network activity stops and restores cookies, files, and the open page. It claims cold restarts under 20 ms. `browser.close()` only drops the WebSocket. https://github.com/kernel/kernel-images
- AWS AgentCore Browser: isolated sessions with a 15-minute default and 8-hour maximum, a WebSocket automation endpoint (Playwright-compatible), Live View, and recording to S3. The browser page itself says "containerized"; AgentCore Runtime docs say each session gets its own microVM, terminated with memory sanitized afterward. https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-tool.html , https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-sessions.md
- Cloudflare Browser Rendering: on the paid plan, 200 concurrent browsers per account and 3 new browsers per second. Idle timeout is 60 s by default, up to 10 min with `keep_alive`, with no fixed maximum lifetime. https://developers.cloudflare.com/browser-rendering/platform/limits/
- Steel-authored benchmark of session create+release: Steel about 229 ms, Browserbase about 367 ms, Kernel about 556 ms, Hyperbrowser about 2,932 ms. The vendor is biased, and p99 runs to multiple seconds. https://steel.dev/blog/remote-browser-benchmark
- Another comparison reports Browserbase session creation averaging about 9.4 s, which conflicts with the Steel benchmark. https://techstackups.com/comparisons/hosted-browser-benchmarks/
- Hyperbrowser runs stealth Chromium in isolated containers. Steel is open source and self-hostable through Docker. The isolation technology of Browserbase and Anchor is not published, UNVERIFIED. https://ai.notte.cc/answers/hyperbrowser-vs-steel

## 7. Snapshotting a running browser
- Kernel: production snapshot and restore of a running headful Chromium in Unikraft microVMs (standby mode). https://github.com/kernel/kernel-images
- Freestyle snapshots a VM after the display, browser, VNC, and CDP are up and healthy. Its unit clears Chromium `Singleton*` lock files on start, because stale profile locks survive snapshots. https://www.freestyle.sh/docs/guides/run-chromium-and-chrome-in-a-sandbox.md
- E2B: a full pause or snapshot keeps memory and running processes. All external connections (WebSocket, PTY) drop and clients must reconnect, so CDP clients must re-dial `/json/version`. https://e2b.dev/docs/sandbox/snapshots , https://e2b.dev/docs/sandbox/persistence
- Pitfalls: identical RNG and `boot_id` across clones (see Firecracker doc above). Wall-clock jumps after restore, which matters for Chrome timers and TLS session expiry (UNVERIFIED). Open TCP/TLS sockets are dead after restore or clone. VFIO GPUs block snapshots unless the driver supports migration v2. https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/random-for-clones.md , https://github.com/cloud-hypervisor/cloud-hypervisor/blob/main/docs/vfio.md
- gVisor checkpoint/restore exists, but issues show edge cases (for example deleted-but-open files fail checkpoint with `--overlay2=none`, a pattern Chrome uses for shm). No documented Chrome-under-runsc checkpoint was found, UNVERIFIED. https://github.com/google/gvisor/issues/11425

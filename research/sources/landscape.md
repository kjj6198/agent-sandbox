## Notes

### Techniques for fast start (with sources)
- **Restore a snapshot instead of booting.** E2B: "A sandbox is a resumed snapshot. Templates are pre-booted VMs (memory, disk, and machine state)... 'Creating' a sandbox means restoring one, not booting a kernel." Fresh creates, resumes, and forks all take the same path. https://github.com/e2b-dev/infra
- **Lazy memory via userfaultfd (UFFD).** E2B: "Memory pages are served lazily on page fault through `userfaultfd`." https://github.com/e2b-dev/infra . Third-party clones such as wrenn copy the design (Firecracker snapshot + UFFD + diff snapshots): https://git.omukk.dev/wrenn/sandbox/src/branch/dev/internal/vm/manager.go
- **Copy-on-write rootfs.** E2B: "the root filesystem is a copy-on-write overlay over a read-only image, so only the data a sandbox actually touches is ever fetched" (combines CoW with lazy fetch from object storage). CodeSandbox: live clone with copy-on-write. https://codesandbox.io/blog/joining-together-ai-introducing-codesandbox-sdk
- **Warm pools.** Azure dynamic sessions (pool of ready, unallocated Hyper-V sessions, refilled automatically), kubernetes-sigs SandboxWarmPool, and Daytona's pre-warmed pool. Kernel did the opposite: by snapshotting pre-booted browsers it "eliminated warm pooling entirely" and cut idle cost to zero. https://unikraft.com/customer-stories/scaling-browser-infrastructure
- **Pre-booted browsers.** Kernel boots Chrome fully, then snapshots the whole VM, so a "new" browser is a restore. https://github.com/kernel/kernel-images
- **Fork/clone of running VMs.** CodeSandbox (memory snapshot + CoW clone), Morph Infinibranch, Freestyle live fork, E2B fork. For agents this enables tree search and rollback.
- **Pause and resume as a cost lever.** Blaxel auto-snapshots after 15 s idle; Sprites hibernate; Kernel goes to standby on no network activity; E2B paused sandboxes do not expire.
- **Bottlenecks named.** Kernel boot plus userspace init, avoided by snapshot (E2B). Fetching image and memory data, avoided by lazy UFFD + CoW (E2B). Pod scheduling and cold pod start in Kubernetes, avoided by warm pools (agent-sandbox). Chrome startup, avoided by pre-booted snapshots (Kernel). For gVisor, Modal says CRIU does not work with runsc, so it had to build on gVisor's own checkpoint/restore. https://modal.com/blog/mem-snapshots

### What leaders converged on, and stated reasons
- **Firecracker** (snapshot-restore microVMs) dominates the dedicated agent-sandbox vendors: E2B, Vercel Sandbox, Fly (Machines and Sprites), CodeSandbox/Together, AWS AgentCore (secondary source), and Kernel's browsers via Unikraft. The shared reason is a dedicated guest kernel for untrusted code plus memory snapshot/restore. CodeSandbox picked Firecracker explicitly for "the unique functionality to pause VMs, snapshot memory to disk, and resume from that state later". https://codesandbox.io/blog/joining-together-ai-introducing-codesandbox-sdk . Vercel: unlike Docker, a "dedicated kernel... stronger isolation". https://vercel.com/docs/sandbox/concepts
- **gVisor** is used by hyperscaler and model-lab platforms that run on Kubernetes or GPUs: Modal (default; GPU sandboxes are gVisor only), GKE Agent Sandbox, Anthropic claude.ai. Modal's reason is security on the container runtime they already ran. Its VM runtime exists for Docker and FUSE, which gVisor handles poorly. https://modal.com/docs/guide/sandboxes
- **Cloud Hypervisor via Kata**: Northflank says it started on gVisor and migrated to Kata microVMs "to balance security and performance". It runs Kata + Cloud Hypervisor where nested virt exists, with gVisor as the fallback (for example on non-metal AWS and GPU nodes). This is the clearest public "moved off gVisor" statement. https://northflank.com/blog/kata-containers-vs-gvisor
- **Hyper-V**: Azure only. **libkrun**: Microsandbox (local-first). **Containers**: Daytona by default.
- No primary E2B post explaining "Firecracker over gVisor" was found (UNVERIFIED). Comparisons that make the case are vendor-adjacent: https://fly.io/learn/firecracker-vs-gvisor.md , https://northflank.com/blog/firecracker-vs-gvisor

### Implications for a self-hosted platform
- Firecracker + UFFD + CoW rootfs + snapshot-as-create is a proven open-source design (E2B runtime, Apache-2.0) and can be self-hosted.
- gVisor gives the easiest Kubernetes path (agent-sandbox + warm pools) and GPU support. Its weak spots are Docker-in-sandbox and FUSE (Modal), plus syscall overhead.
- Cloud Hypervisor appears mainly through Kata (Northflank). No vendor publishes Cloud Hypervisor snapshot-restore start numbers comparable to E2B's.
- Browsers: the fastest product (Kernel) snapshots a pre-booted Chrome VM. The same technique ports to Firecracker.
